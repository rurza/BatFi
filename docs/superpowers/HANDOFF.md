### 4a. Queued fix in `SMCService.swift` — do this FIRST after P3.3 lands

From Phase 2's fix re-review. All three were blocked only because P3.3 owns the file.

- **A — relax the unmeasured legacy gate.** `CH0I`/`CH0J` are gated on `ui8 `/1 taken from the `SMCKey` *declaration*; `CH0I` is absent on the dev Mac and `CH0J` is privilege-gated, so neither was measured. Guessing the type wrong silently disables force discharge across the entire Intel fleet **and**, post-reorder, makes `restoreSystemDefaults()` throw on every disengage there. Relax that arm to **size + attributes only, any type**. Be strict where measured, permissive where not. Also accept `hex_` **or** `ui8 ` at size 1 for `CHIE`, to cover firmware variation on a one-machine measurement. `SMCKeyCapability.matches` has no "any type" mode — needs an overload in `Shared` or inline field checks.
- **C — make `restoreSystemDefaults()` best-effort per step.** The two writes target disjoint keys with no precedence, so all-or-nothing only decides *which* safety write gets stranded. Real regression: `ChargingManager.disengage()` skips `updateChargingMode(.charging)` when it throws, so the hardware gets restored by `resetIfPossible()` while the app's mode goes stale. Attempt both, report a combined result, keep release-first ordering and `resetIfPossible()` in the failure path.
- **D — the load-bearing `"hex_"` literal has no test.** It is the single string deciding whether force discharge works on every current Mac, and nothing pins it. A future "cleanup" aligning it to the `SMCKey` declaration would silently disable force discharge **with a green suite**. Lift the expected key shapes into `Shared` beside `ChargeBackendResolver` so they are testable and colocated with the `CHTE`/`CH0B`/`CH0C` shapes.
- Minor: the comment near `forceDischargeKeyIsUsable` claims the read and write gates can never disagree, but they differ on `writable:`, so a readable-but-not-writable `CH0I` makes the read pass while the write refuses.

### 4c. Phase 4 — `docs/superpowers/plans/2026-08-04-phase4-golden-gate.md`

The `bfD0`/`bfE0`/`bfF0` firmware-managed range. Read the plan; the traps are documented there. Highlights:

- **Ranked FIRST**, ahead of `CHTE` — an older macOS can carry newer firmware.
- **Percentages are little-endian** ui32, against normal SMC convention. 50% is `32 00 00 00`.
- **Write order is firmware-mandated**: `bfF0←00`, `bfD0←upper`, `bfE0←lower`, `bfF0←02`.
- **`bfF0` must be added to `resetIfPossible()`** — see the invariant in §5.
- **MEASURE the key shapes before hardcoding them.** `SMCKey` declarations in this repo do not reliably match firmware; `CHIE` is declared `ui8 ` but measures `hex_`. Nobody here has macOS 27 hardware, so these are unmeasured.
- Beta 4 firmware (`20457.0.125.0.2`+) moved the key set again. The probe simply will not match there and falls through — no version check needed. That is intentional.

## 5. The one pattern that matters

**Seven instances of the same bug class surfaced this session.** Every one was a place where the same fact — *what shape is this key, and what value means engaged* — is encoded in more than one location with nothing forcing agreement:

1. `CHIE` written `0x08`, read back against `1`.
2. Probe gates using bare string literals beside operations using `SMCKey` constants.
3. Legacy write gate on `CH0J`, read gate on `CH0I`.
4. **`resetIfPossible()` cleared every force-discharge key except `CHIE`** — a Mac could be left draining on AC after quit. The dangerous one.
5. `MCLStatus.supported` vs `isMCLSupported` — two questions, one name.
6. `CHIE` declared `ui8 `, measures `hex_` — hardcoding the declaration would have disabled force discharge on every current Mac.
7. The measured `"hex_"` literal has no test pinning it (still open, §4a-D).

**Invariants to state up front in every future task touching SMC:**

- One `SMCKey` constant per key; gates derive from it via `probeCapability(for:)`, never a bare string.
- Every gate uses `matches(type:size:writable:)`, not mere existence — **but only with measured shapes**.
- **Every key any engage path writes must also be cleared by `resetIfPossible()`.**
- Never gate on the macOS version. Behaviour tracks firmware: installing macOS 27 on any volume reflashes firmware for the whole Mac, downgrading macOS does not roll it back, and macOS 26.6 / 15.7.8 / 14.8.8 ship identical firmware.

## 8. Known follow-ups for 3.1.3+ (deliberately not in scope)

- `isRunningOnLaptop()` in `PowerSourceClient+Live.swift` is the last un-retried, un-degraded IOKit gate and it **terminates the app** with no log line. Same bug class Phase 1 removed everywhere else, left in the one place that is unrecoverable.
- Battery health parses the English string `"Maximum Capacity"`, so on a non-English Mac it never matches; `store(nil)` discards the failure, so every IOPS notification re-spawns a ~1 s `system_profiler`. Fix with a failure timestamp, or parse `system_profiler -json` (`sppower_battery_health_maximum_capacity` is not localized).
- Phase 1's coalescing drop window: ≤1 stale sample, self-correcting at the next 1% change, so ≤1% limit overshoot. ~4-line fix (a `pendingRerun` flag).
- `SMCKit.close()` does not zero `SMCKit.connection`, so a stale `io_connect_t` survives a close.
